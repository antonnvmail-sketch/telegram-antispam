Telegram-бот для текстовой модерации: классифицирует сообщения как `spam`/`ham`, при включённом рабочем режиме удаляет уверенный спам и отправляет подозрительные сообщения администраторам. Основа — TF-IDF и логистическая регрессия.

Публичная копия подготовлена из работающего авторского проекта. Здесь **нет реальных переписок, рабочей БД, модели, токенов и серверных резервных копий**. Вместо них — 200 вымышленных демонстрационных сообщений: 100 spam и 100 ham. Проект начат 25 сентября 2025 года.

Эти примеры нужны для первого запуска. Перед использованием добавьте спам и обычные сообщения, характерные для вашей группы, обучите свою модель и проверьте решения в пробном режиме. Настройка не исключает ошибок: бот помогает модераторам, но не обещает распознавать любой спам. Рабочая модель автора и стартовая демонстрационная модель — разные модели.

## Возможности и ограничения

- Проверка текстовых сообщений в заданных `CHAT_IDS`; slash-команды пропускаются.
- Добавление примеров администраторами, обучение, статистика и локальный импорт размеченного TXT.
- Пробный режим `DRY_RUN=true`: предложенные действия записываются в локальную БД, автоматические удаления и рассылки модераторам отключены. Команды бота по-прежнему могут отвечать пользователю и менять обучающий набор.

Демонстрационная модель не предназначена для немедленного включения автоматических удалений в реальной группе. Возможны ложные удаления и пропуски; контекст родительского поста и смысл флешмобов модель не знает. Качество на независимых реальных данных не измерено.

Обычная фильтрация обрабатывает только `message.text`: изображения, видео, голосовые, подписи к медиа и отредактированные сообщения не проходят автоматическую текстовую модерацию. Загрузка датасета документом через Telegram пока не реализована.

## Что нового в 1.0.3

- `/stat_export` выгружает месячные агрегаты в CSV без текстов и идентификаторов; `/review_stats` показывает количество ответов. `/help` дополнена.

При `DRY_RUN=true` карточки действий и их обработка отключены, включая старые кнопки. Для диагностики используйте `/test_spam`. Пороги и логика классификации сохранены; независимое улучшение точности не заявляется.

## Что нового в 1.0.2

После `/add_spam` и `/add_ham`, а также в `/status` бот показывает количество новых примеров, ещё не включённых в загруженную модель. Учитывается и локальный импорт, включая повторные примеры. Сохранение новой модели выполняется с заменой файла только после завершения записи. При ошибке записи прежний файл остаётся доступен. Добавлена английская инструкция, упрощён состав самостоятельного бота.

## Что нового в 1.0.1

- Решение, попытка удаления, результат Telegram, журнал и уведомление учитываются отдельно. Сбой SQLite или уведомления не превращает успешное удаление в ошибку удаления. Таймаут отмечается как неизвестный результат; автоматических повторов нет.
- Фильтр и `/test_spam` используют общую функцию. Сохраняются P(spam), метка/уверенность, действие, причина, пороги, версия политики, UUID, UTC-время, SHA256 входа и **загруженного** файла модели. Хеш вычисляется по тем же байтам, которые загружаются в память.
- Таблица `moderation_decisions` различает source=filter/test_spam и dry_run=0/1. В пробном режиме запись action=delete не означает фактического удаления; старый журнал дополнительно содержит события would_*.
- `/status` показывает версии бота и модели. Диагностика показывает рекомендацию, вероятность, причину, пороги, версию и результат записи без удаления и рассылки.

DRY_RUN=true по умолчанию. Условия выбора действия и пороги 0.7/0.4 сохранены. Это техническая стабилизация; исправление всех ложных срабатываний, анализ авторов и новая политика книг/коротких реплик не заявляются.

Совместимые Python/зависимости тоже нужны отдельно; восстановление исходников и БД не равно восстановлению чистой ОС.

Авторский экземпляр обновлён отдельно; диагностика сверена с БД, а возврат прежнего кода с сохранением новых записей проверен в изолированной копии с фиктивным Telegram. Публикация не меняет работающий сервер и не подтверждает живую работу публичной копии в вашей среде.

## Быстрый старт без подключения к Telegram

Скачайте архив исходников из выпуска 1.0.1 и распакуйте его либо клонируйте репозиторий:

```shell
git clone https://github.com/antonnvmail-sketch/telegram-antispam.git
cd telegram-antispam
```

Требуется Python 3.12. Основные зависимости перечислены в requirements.txt, точные проверенные версии всех зависимостей — в requirements.lock.txt, который используется как constraints при установке. Тестирование проводилось. Выполняйте команды из корня проекта. На Windows используйте `python`, если Python доступен под этим именем; в Linux при создании окружения может потребоваться `python3.12`.

```shell
python -m venv .venv
```

Активируйте окружение:

```powershell
# Windows PowerShell
.\.venv\Scripts\Activate.ps1
```

```shell
# Linux / macOS
source .venv/bin/activate
```

Если PowerShell запрещает активацию, можно обращаться напрямую к `.\.venv\Scripts\python.exe` вместо `python`, не меняя системную политику.

```shell
python -m pip install -r requirements.txt
python -m pip check
python prepare_demo.py
```

Последняя команда читает только `data.example.txt`, создаёт локальные `dataset.sqlite` и `model.joblib` и обучает новую модель. Токен не нужен, бот не импортируется, Telegram не вызывается. Существующие файлы не перезаписываются. Для повторного эксперимента задайте новые пути:

```shell
python prepare_demo.py --db another-demo.sqlite --model another-demo.joblib
```

Это проверка механизма обучения, не оценка точности. Обученная модель и БД исключены из Git. Загружайте joblib только из доверенного источника: десериализация моделей выполняет Python-код.

## Подключение своего бота

1. Создайте собственного бота через BotFather и отдельную тестовую группу.
2. Скопируйте `.env.example` в `.env`, например `Copy-Item .env.example .env` в PowerShell или `cp .env.example .env` в Linux.
3. Заполните `TELEGRAM_TOKEN`, `ADMIN_IDS` и `CHAT_IDS` собственными значениями. ID — числа через запятую, не имена `@username`; для групп ID может быть отрицательным. Настройте получение групповых сообщений и права бота в BotFather/группе. Для реального удаления позже потребуются права администратора на удаление сообщений.
4. Сохраните `DRY_RUN=true`, а необязательные настройки оставьте со значениями из примера.
5. Запустите **единственный экземпляр**:

```shell
python bot_new.py
```

Бот сначала проверяет токен, списки ID, пороги и наличие локальной модели. Без подготовки выдаёт ошибку до создания рабочих файлов. Пустой `.env.example` не является готовой конфигурацией запуска.

После проверки примеров и ошибок в тестовой группе можно отдельно решить, включать ли автоматическую модерацию: `DRY_RUN=false` и перезапуск. Для остановки — Ctrl+C. Никогда не подключайте демонстрационный экземпляр к токену уже работающего бота.

### Настройки

| Переменная | Назначение |
| --- | --- |
| `TELEGRAM_TOKEN` | Секрет собственного бота; только в локальном `.env` |
| `ADMIN_IDS` | Пользователи, которым разрешены команды обучения и диагностики |
| `CHAT_IDS` | Разрешённые чаты для текстового фильтра |
| `DATASET_PATH` / `MODEL_PATH` | База примеров/решений и доверенная локальная модель |
| `DRY_RUN` | По умолчанию true: только запись предполагаемых действий |
| `SPAM_DELETE_THRESHOLD` | 0.7 по умолчанию |
| `SPAM_MODERATE_THRESHOLD` | 0.4 по умолчанию |
| `LOG_FILE`, `LOG_MAX_BYTES`, `LOG_BACKUP_COUNT` | Ротация локального журнала |

Действие выбирается, только если предсказана метка `spam` и уверенность **строго больше** соответствующего порога. Это унаследованная логика, не гарантия статистически откалиброванной вероятности. Порог 0.4 не означает, что все сообщения с P(spam)>0.4 отправляются на модерацию: сначала должна победить метка spam.

## Свои обучающие примеры

Формат UTF-8: `spam текст` или `ham текст`, одна запись на строку. Не добавляйте реальные чужие сообщения без законного основания/разрешения. Не считайте автоматически правильными решения самого бота.

Администраторы могут использовать `/add_spam текст` и `/add_ham текст`. Они добавляют примеры в БД; `/train` обучает модель на текущей таблице messages и перезагружает её. Нужны оба класса и достаточно повторяющихся признаков. Обучение синхронное и на большом наборе может задерживать ответы бота.

Локальный импорт, пока бот остановлен:

```shell
python import_dataset.py --data my-data.txt --db dataset.sqlite
```

Импорт проверяет весь файл до записи и создаёт таблицы при необходимости. Он **добавляет** строки: повторный импорт дублирует примеры. После изменения БД модель нужно переобучить. Команда бота `/import_data` читает локальный файл `data.txt`; этот файл не поставляется и исключён из Git.

Команды `/stats`, `/status`, `/check_permissions`, `/test_spam текст` доступны администраторам; `/here` показывает ID текущего чата. `/start` и `/help` показывают справку. `/evaluate` считает отчёт на той же БД, что используется для обучения: **это не независимая оценка качества**. Для такой оценки подготовьте отдельный размеченный набор, не использовавшийся в обучении.

`/test_spam` только проверяет переданный текст: показывает метку, уверенность и рекомендацию. Команда не удаляет сообщения и не отправляет их на модерацию. При `DRY_RUN=true` ответ дополнительно отмечает пробный режим.

## Данные и Git

Отдельная база `<DATASET_PATH>.admin-review.sqlite` содержит исходные тексты карточек, версии решений, идентификаторы и обратную связь. Не добавляйте её или её служебные файлы в Git.

moderation_decisions хранит метаданные решения, SHA256 текста и ID чата/сообщения без исходного текста и username; структурированные файловые события содержат эти метаданные. База logs содержит тексты сообщений и идентификаторы. База messages — обучающие тексты. Журналы ошибок также могут содержать данные сообщений. Не публикуйте рабочие `.env`, TXT, SQLite, joblib, логи, окружения и резервные копии. `.gitignore` помогает с обычными именами файлов, но не распознаёт любые секреты и произвольные имена датасетов. Проверяйте `git diff --cached` и `git status` перед коммитом.

## Автозапуск и контроль состояния (необязательно)

Для сервера с пользовательским systemd предусмотрен `setup_service.py`. Сначала просмотрите формируемые файлы, используя Python из выбранного окружения:

```shell
python setup_service.py
python setup_service.py --write
```

`--write` создаёт три файла в `~/.config/systemd/user` и отказывается перезаписывать существующие. Службы пока не запускаются. Пути формируются по расположению проекта и текущему Python. Если после этого переместить проект или окружение, пути нужно обновить.

Остановите вручную запущенный экземпляр и выполните:

```shell
systemctl --user daemon-reload
systemctl --user enable --now antispam.service antispam-health.timer
systemctl --user status antispam.service
```

Для запуска после загрузки без входа пользователя администратор сервера должен включить linger для выбранной учётной записи (`loginctl enable-linger USER`). Служба автоматически перезапускает завершившийся процесс и следит за зависанием главного цикла. После частых сбоев действует ограничение повторных стартов; устраните причину и используйте `systemctl --user reset-failed antispam.service` перед новым запуском. Намеренный `systemctl --user stop antispam.service` не вызывает перезапуск.

Проверка состояния выполняется раз в минуту, прав удаления — раз в пять минут. Тишина в чатах не считается неисправностью: контролируется успешный ответ получения событий. Администраторы получают уведомления об изменениях состояния, без постоянных сообщений «всё хорошо». При недоступности самого сервера или Telegram доставка уведомления может быть невозможна. При неоднозначной ошибке доставки одинаковое уведомление не повторяется автоматически.

Управление: `systemctl --user restart antispam.service`; журнал: `journalctl --user -u antispam.service`. Перед намеренным обслуживанием остановите `antispam-health.timer`, после верните его. Не запускайте второй polling с тем же токеном. Локальный статус в `.operations/` не добавляйте в Git.

## Оценка на отдельной выборке

Для оценки подготовьте размеченный UTF-8 TXT с обоими классами `spam` и `ham`, который не использовался при обучении. Размечать должны люди по правилам вашей группы; решение самого бота не является эталоном. Держите близкие шаблоны в одной выборке и фиксируйте модель до проверки. Чужие сообщения и файлы с результатами не добавляйте в репозиторий.

```shell
python evaluate_holdout.py --model trusted-model.joblib --training-data training.txt --data holdout.txt
```

Скрипт не обучает модель и не вызывает Telegram. Используйте только доверенный joblib-файл. В `--training-data` нужно передать фактические обучающие примеры этой модели. Скрипт отклоняет точные совпадения текстов после нормализации регистра/пробелов и дубли в контрольной выборке. Он не может проверить историю обучения модели или автоматически исключить все близкие шаблоны.

JSON-отчёт содержит матрицу ошибок классификатора, количество предложенных действий, точность удалений, долю удалённого спама и долю ошибочных удалений нормальных сообщений. Пороги задаются `--delete-threshold` и `--moderate-threshold` (по умолчанию 0.7 и 0.4); действия считаются по той же логике, что у фильтра. При отсутствии предложенных удалений их точность равна `null`. Тексты сообщений в отчёт не выводятся. Эти числа характеризуют только предоставленную размеченную выборку; на синтетических примерах они не доказывают качество в реальной группе.

## Развитие

Проект остаётся открытым для доработок: можно сообщать об ошибках через Issues и предлагать изменения через Pull Requests. Не прикладывайте токены, реальные переписки, базы или обученные на чужих сообщениях модели.

Возможные направления — независимая контрольная выборка, контекстная модерация и работа с медиа. Это направления развития, а не обещание готовых функций. Возможности ручной модерации и контроля состояния вошли в 1.0.3; дальнейшее улучшение точности требует отдельных данных и проверок. Сроков и графика следующих релизов нет. См. [CHANGELOG.md](CHANGELOG.md) для истории и отличий открытой копии от работающего исходного проекта.
